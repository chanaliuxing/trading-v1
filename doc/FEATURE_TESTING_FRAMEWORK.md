# Feature Engineering Testing Framework

## Overview

This document describes the three-layer testing framework for feature engineering in the trading system. The framework ensures that features are validated at multiple levels before being used in production ML models.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 3: AI Brain Proposal Validation                       │
│ - DSL compilation testing                                   │
│ - Schema validation (dry_run_feature_expr)                  │
│ - Small window data quality checks                          │
│ - OOF/HPO performance validation                            │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│ Layer 2: Pipeline Integration Tests                         │
│ - ClickHouse → features_1m → enhanced features              │
│ - Coverage checks (non_null_ratio)                          │
│ - Value range validation                                    │
│ - Backfill verification                                     │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│ Layer 1: Single Operator Unit Tests                         │
│ - Individual feature function correctness                   │
│ - Synthetic data with known properties                      │
│ - Edge case handling (NaN, zero, extreme values)            │
│ - No external dependencies (pure Python)                    │
└─────────────────────────────────────────────────────────────┘
```

## Tools

### 1. DSL Compilation Tester

**File**: `tools/test_feature_dsl_from_llm.py`

**Purpose**: Test feature DSL specifications generated by Claude/GPT/Brain to ensure they compile to valid SQL.

**Usage**:
```bash
venv/bin/python tools/test_feature_dsl_from_llm.py tests/fixtures/dsl_test_cases.json
```

**Input**: JSON array of test cases
```json
[
  {
    "name": "ret5_over_atr14",
    "dsl": {
      "op": "ratio",
      "num": "f.ret_5",
      "den": "f.atr_14",
      "eps": 1e-06
    }
  }
]
```

**Output**: `cases.out.json` with compilation results
```json
[
  {
    "name": "ret5_over_atr14",
    "ok": true,
    "sql": "(f.ret_5) / nullIf(f.atr_14, 1e-06)"
  }
]
```

### 2. Feature Quality Verifier

**File**: `tools/verify_feature_experiment.py`

**Purpose**: Verify that feature columns in ClickHouse have reasonable coverage and values after pipeline processing.

**Usage**:
```bash
venv/bin/python tools/verify_feature_experiment.py \
  --symbols TSLA,NVDA \
  --feature-cols corr_spy_20,beta_spy_20 \
  --start 2025-11-20 \
  --end 2025-11-25 \
  --table trading.features_1m \
  --out report.json
```

**Output**: JSON report with quality metrics
```json
[
  {
    "symbol": "TSLA",
    "feature": "corr_spy_20",
    "total_rows": 3200,
    "non_null": 3180,
    "non_null_ratio": 0.9937,
    "min": -0.8,
    "max": 0.95,
    "mean": 0.45,
    "std": 0.25,
    "all_zero": false,
    "all_constant": false
  }
]
```

## Test Suites

### Unit Tests

**File**: `tests/unit/features/test_feature_dsl_sql.py`

Tests DSL compilation for all supported operations:
- `ratio`, `ratio_minus_1`
- `log1p`
- `product`, `sum`
- `abs`
- Nested operations
- Multi-frame features (f, m5, d aliases)

**Run**:
```bash
pytest tests/unit/features/test_feature_dsl_sql.py -v
```

**File**: `tests/unit/features/test_feature_engineering_pipeline.py`

Tests individual feature calculation functions:
- Multiframe features (ret_5m, vol_15m, etc.)
- Relative strength features (ret_vs_spy, beta_spy_20)
- Microstructure features (vwap_dist, volume_surge)
- Volatility features (realized_vol)
- Time features (is_first_30min, is_lunch_time)

**Run**:
```bash
pytest tests/unit/features/test_feature_engineering_pipeline.py -v
```

### Integration Tests

Integration tests that require ClickHouse are marked with `@pytest.mark.integration`.

**Run**:
```bash
pytest tests/unit/features/ -m integration -v
```

## Workflow for New Features

### For AI Brain-Proposed Features

When the Brain proposes a new feature, it goes through this validation pipeline:

#### Stage 1: DSL Compilation ✅ (Fast, no DB required)

```python
from libs.features.feature_dsl_sql import dsl_to_sql

dsl_spec = {
    "op": "ratio",
    "num": "f.ret_5",
    "den": {"op": "abs", "col": "f.atr_14"},
    "eps": 1e-06
}

try:
    sql = dsl_to_sql(dsl_spec)
    print(f"✅ Compiled: {sql}")
except FeatureDSLCompileError as e:
    print(f"❌ Compilation failed: {e}")
    # Reject feature, provide error back to Brain
```

#### Stage 2: Schema Validation ✅ (Fast, lightweight DB query)

```python
from scripts.ai_trader.brain.tools_sql import dry_run_feature_expr

result = dry_run_feature_expr(
    expr=sql,
    sources=["m5"],  # If using m5.* features
    sample_symbol="TSLA",
    limit=10,
)

if not result["ok"]:
    if result["error_type"] == "SchemaValidationError":
        print(f"❌ Column not found: {result['error_message']}")
        # Reject feature, Brain needs to fix column names
    else:
        print(f"❌ Query failed: {result['error_message']}")
```

#### Stage 3: Small Window Experiment 🔄 (Slow, requires backfill)

```bash
# Queue a small window backfill job
venv/bin/python tools/backfill_enhanced_features.py \
  --symbols TSLA,NVDA \
  --start 2025-11-20 \
  --end 2025-11-23 \
  --batch-days 3 \
  --only-cols new_feature_name

# Verify quality
venv/bin/python tools/verify_feature_experiment.py \
  --symbols TSLA,NVDA \
  --feature-cols new_feature_name \
  --start 2025-11-20 \
  --end 2025-11-23 \
  --out runs/ai_trader/feature_checks/new_feature_report.json
```

**Quality Gate Criteria**:
- ✅ `non_null_ratio > 0.5` (at least 50% coverage)
- ✅ `all_zero == false` (not all zeros)
- ✅ `all_constant == false` (has variance)
- ✅ Values in reasonable range (no extreme outliers)

#### Stage 4: OOF/HPO Validation 🔄 (Slowest, requires training)

Only after passing stages 1-3, the feature is added to the main catalog and included in OOF/HPO experiments.

```yaml
# config/features_catalog.json
{
  "candidates": [
    {
      "name": "new_feature_name",
      "expr": "(compiled SQL from stage 1)",
      "required_sources": ["m5"],
      "tags": ["experimental"],
      "default_exposed_to_llm": false
    }
  ]
}
```

After proving positive IC/IR in OOF, set `default_exposed_to_llm: true`.

### For Manual Feature Engineering

When developers add new features to `FeatureEngineerV2`:

1. **Write unit test** in `test_feature_engineering_pipeline.py`:
   - Create synthetic data with known properties
   - Call the feature function
   - Assert expected behavior

2. **Run tests locally**:
   ```bash
   pytest tests/unit/features/test_feature_engineering_pipeline.py::TestFeatureOperatorCorrectness::test_your_new_feature -v
   ```

3. **Verify in small window**:
   ```bash
   venv/bin/python tools/backfill_enhanced_features.py \
     --symbols TSLA \
     --start 2025-11-20 \
     --end 2025-11-21 \
     --batch-days 1
   ```

4. **Check coverage**:
   ```bash
   venv/bin/python tools/check_feature_column_coverage.py \
     --symbols TSLA \
     --days 1
   ```

## Best Practices

### Writing DSL Test Cases

1. **Name descriptively**: `"nested_product_in_ratio"` not `"test_1"`
2. **Add descriptions**: Explain what the test validates
3. **Cover edge cases**: Empty lists, None values, extreme nesting
4. **Test real patterns**: Use actual feature engineering patterns from production

### Writing Feature Unit Tests

1. **Use synthetic data**: Create data with known properties (linear trends, surges, etc.)
2. **Test direction, not exact values**: `assert result > 0` not `assert result == 0.123`
3. **Include warmup periods**: Rolling windows need warmup, skip first N rows
4. **Test NaN handling**: Inject NaNs and verify graceful handling

### Feature Quality Standards

| Metric | Threshold | Action if Failed |
|--------|-----------|-----------------|
| `non_null_ratio` | > 0.95 | ✅ Excellent |
| `non_null_ratio` | 0.5 - 0.95 | ⚠️ Acceptable, investigate |
| `non_null_ratio` | < 0.5 | ❌ Reject feature |
| `all_zero` | false | ❌ Reject if true |
| `all_constant` | false | ❌ Reject if true |
| `extreme_outliers` | < 0.1% | ⚠️ Investigate if higher |

## Troubleshooting

### DSL Compilation Fails

**Error**: `Unknown DSL op: my_custom_op`

**Solution**: Only supported ops are allowed. See `libs/features/feature_dsl_sql.py` for the list. If you need a new op, extend the DSL compiler first.

### Schema Validation Fails

**Error**: `column 'new_col' not found for alias 'f' in table trading.features_1m`

**Solution**: The column doesn't exist in ClickHouse. Either:
1. Run the feature backfill pipeline to create it
2. Use an existing column name
3. Add the column to the base features table

### Low Coverage in verify_feature_experiment

**Problem**: `non_null_ratio = 0.2`

**Possible causes**:
1. Feature calculation failing due to missing dependencies
2. Long warmup period (check rolling window sizes)
3. Data quality issues in upstream bars

**Debug**:
```bash
# Check raw feature values
clickhouse-client --query "
  SELECT ts, symbol, new_feature_name
  FROM trading.features_1m
  WHERE symbol = 'TSLA'
    AND ts >= '2025-11-20'
    AND ts < '2025-11-21'
  ORDER BY ts
  LIMIT 100
"
```

### All-Zero or All-Constant Features

**Problem**: `all_zero: true` or `all_constant: true`

**Possible causes**:
1. Division by constant in DSL (e.g., `den: 1.0`)
2. Feature calculation error (check logs)
3. Missing SPY data for relative features
4. Time window contains no market hours

**Debug**: Test the feature on a known-good sample manually:
```python
from libs.features.feature_engineer_v2 import FeatureEngineerV2
import pandas as pd

# Load sample data
df = ... # your sample DataFrame

result = FeatureEngineerV2.compute_all_features(df)
print(result['your_feature'].describe())
```
