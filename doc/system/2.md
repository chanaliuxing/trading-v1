# 交易系统重写规范（Spec v1.0，高层）

## 0. 目标与范围

* **目标**：重写成一个**事件驱动、控制反转（IoC）**的模块化量化平台，支持**多策略并发、互不干扰、策略级资金池与风控**，在**5–10秒微周期**上做决策与执行，具备**企业级可观测性、容错与对账恢复**，回测与实盘**口径一致**。
* **范围**：策略引擎、数据服务、执行服务、风控服务、组合账本、对账恢复、控制面与运维、数据存储、回测模拟器。
* **不在本次范围**：跨资产衍生品定价库、跨券商路由（留接口）、机器学习训练平台（留接口）。

## 1. 成功指标（SLO/KPI）

| 维度                            | 目标                                 |
| ----------------------------- | ---------------------------------- |
| **端到端延迟**（MicroBar → 决策 → 发单） | P95 ≤ 500ms                        |
| **执行安全**                      | OCO 丢失/方向错配 = 0；“无保护窗口”>1s = 0     |
| **正确性**                       | 重复/漏单 = 0；幂等冲突 = 0                 |
| **对账恢复**                      | 冷启动 ≤ 5 分钟恢复到可交易；无“幽灵/孤儿”遗留        |
| **风控严格性**                     | 策略资金池不超限；订单级资金预留与终态释放严格平衡          |
| **数据完整性**                     | 当日 1m 完整 ≥ 99.9%；5–10s 修洞成功率 ≥ 99% |
| **回测一致性**                     | 状态序列对齐测试通过（核心策略）                   |
| **可用性**                       | 核心服务 99.9% 月可用；崩溃自动重启并报警           |

## 2. 架构总览（IoC + 服务化）

核心思想：**控制反转**。中央**交易引擎（Trading Engine）**提供运行时与 API，策略作为插件被动响应事件；周边能力（数据、风控、执行、账本、对账、控制面）以**独立服务**接入**事件总线**与**控制总线**。

```
[Data Service] --bars/micro--> (Event Bus) --> [Trading Engine] --order.req-->
                                                       |                     \
                                               --status/fill--> (Event Bus)   \--> [Risk Service] approve/deny
                                                       |                         \
                                             [Portfolio Service] <--- fills ------ [Execution Service] --> IBKR
                                                        ^
(State Bus / Control Bus) <--> [System Manager / Supervisor] <--> [Dashboard API]
```

### 2.1 总线分层

* **Event Bus（事件总线，Kafka）**：行情、计划、订单请求、状态、成交、健康等**业务事件**（可重放、幂等）。
* **State/Control Bus（控制总线）**：启停/熔断/限流/拉取状态等**控制命令**（强幂等、回执）。

---

## 3. 组件职责（高层规范）

### 3.1 交易引擎（Trading Engine, IoC Runtime）

**职责**

* 承载**策略插件**的生命周期与回调；提供**Execution API**与**State API**。
* 订阅行情/状态事件，调用策略 `OnBar/OnMicroBar/OnOrderUpdate/OnPositionUpdate`。
* 将策略发出的 `MarketOrder/Limit/StopLimit/Cancel/Liquidate` 翻译为**订单请求事件**，送往风控。

**策略基类（最小 API）**

* 事件处理：`Initialize()`, `OnBar(bar1m)`, `OnMicroBar(bar5s/10s)`, `OnOrderUpdate(order)`, `OnPositionUpdate(pos)`, `OnShutdown()`
* 交易 API：`MarketOrder`, `LimitOrder`, `StopLimit`, `Cancel`, `Liquidate`, `Subscribe(symbol, resolution)`, `History(symbol, periods)`
* 状态 API：`self.Portfolio`（从组合服务），`Positions`, `OpenOrders`

**并发与隔离**

* 多策略并发；**每策略/每标的细粒度锁**；策略间**互不共享**上下文（仅通过事件交互）。
* **参数加载与哈希**：策略启动时从配置与 overrides 装配，计算 `param_hash`，写入日志与事件，用于复现与追踪。

---

### 3.2 数据服务（Data Service）

**职责**

* IBKR 实时 5s RTBars，聚合成 **1m** 与 **5s/10s MicroBar**；**today-so-far 回补**与**缺口修复**；RTH/ETH 标签。
* 仅向**活跃集合**（持仓或待入场）发布 `NewMicroBarEvent`，降低压力。

**SLO/约束**

* MicroBar 事件端到端 P95 ≤ 300ms（不含下单路线）。
* 缺口巡检与回补：后台异步；失败报警并可降级（暂停新开仓，仅平仓）。

---

### 3.3 风控服务（Risk Service）

**职责**

* **事前审批**：接收 `order.request`，基于**策略资金池**与**订单级资金预留**、集中度、板块暴露、黑名单、时间窗等规则**approve/deny**。
* **订单级预留**：审批通过→在账本内**预留资金**（含佣金与滑点缓冲），订单终态→**释放**。
* **策略资金池**：`capital_limit_usd / reserved / realized / unrealized`，每策略独立账。
* **互斥/限速**：可配置 `symbol_exclusive`、撤改速率上限、订单数上限。
* **分布式锁**：审批路径使用 **PG Advisory Lock**（策略或策略×标的维度）确保“查-改-写”原子。

---

### 3.4 执行服务（Execution Service）

**职责**

* 消费 `order.request.approved`，与 IBKR 交互下单/撤单，产生日志与 `order.status/fill`。
* **OCO 即时保护**：子单**首次成交**即刻挂 OCO（止损/止盈），数量与方向随净仓动态调整；修改失败→取消重下。
* **止损体系（分层）**：

  1. **灾难硬停（Stop-Market）**：始终在场、独立 OCA 组；跳空/盘口塌陷优先保护。
  2. **自适应追踪（Stop-Limit）**：基于 microATR 与极值，**去抖**（M 个 microbar 连续成立）、**死区**（最小步进 tick）、**撤改节流**（最小间隔、每分钟上限）。
  3. **盈亏转换/超时**：达到 R1 抬 BE；R2 收紧追踪；time-stop 秒/5s 级到点。
     未成交 N 个 microbar 或流动性恶化 → **升级市价**兜底。
* **Meta-Order（TWAP/VWAP/POV）**：拆单曲线、子单跟价与撤改节流、执行期间的**互斥策略**与降级退出。
* **订单巡检协程**：每 3–5s 巡检“应取消未取消/应修改未修改”，强制清理，保证无保护窗口。

---

### 3.5 组合服务（Portfolio Service）

**职责**

* 监听 `fills`，维护**权威**的持仓/均价/现金/实时与已实现 PnL；提供快照给引擎与控制面。
* **持仓计算**采用**有符号数量**（BUY=+qty，SELL=−qty），反转 = 先平旧仓再重置均价。
* 提供**对账核对**接口（预留账 vs 终态释放一致性）。

---

### 3.6 对账恢复（Reconciliation Service）

**职责**

* 冷启动/异常重连：

  * **孤儿领养**（IB 真实挂单→permId/orderRef 精确或模糊匹配）；
  * **幽灵清理**（DB 有、IB 无→标记 STALE_CLOSED）；
  * **上下文重建**（order_map、pos/avg_px、OCO）。
* **安全阈**：价格容忍度（bps）、时间窗、最大自动动作数；失败回滚策略；可视化与审计日志。

---

### 3.7 控制面与监督（Dashboard API & System Manager）

**职责**

* **Dashboard API（FastAPI）**：状态查询、度量拉取、（受 RBAC 控制的）启停/熔断/限速等操作。
* **System Manager / Supervisor**：进程级守护（交易进程 & 控制面），崩溃自动重启（退避策略）、心跳丢失触发**只许平仓**与告警；通过 **Control Bus** 下发命令并接收回执。

---

### 3.8 回测模拟器（Backtest/Simulator）

**职责**

* 与实盘**同构事件与状态机**：限价撮合（按下一根 bar 高/低）、滑点/手续费模型、TWAP/VWAP/POV 拆单曲线、5–10s 微周期撮合。
* **状态序列对齐测试**：回放真实事件，校验策略触发→撮合→OCO→止损→平仓的序列一致性。

---

## 4. 数据与事件（高层 Schema）

### 4.1 事件主题（建议命名）

* 市场数据：`md.bar.1m.v2`、`md.bar.micro.v2`（字段含 `freq=5s|10s`、RTH/ETH 标志）
* 策略计划：`engine.plan.v2`、`engine.plan.approved.v2`
* 订单与成交：`exec.order.request.v2`、`exec.order.approved.v2`、`exec.order.status.v2`、`exec.fill.v2`
* 风控决定：`risk.decision.v2`（approve/deny, reason）
* 组合快照：`portfolio.snapshot.v2`
* 健康与控制：`health.heartbeat.v2`、`control.command.v2`、`control.ack.v2`

### 4.2 事件结构（统一骨架）

* `schema_v`: int（版本）
* `metadata`: `{event_id, ts_utc, producer, idempotency_key?, partition_keys, rth_flag?}`
* `data`: 业务载荷（随主题而变）
* **幂等/去重**：所有“可产生副作用”的事件必须带 `idempotency_key`；fills 以 `(order_id, ts, qty, price)` 唯一去重。
* **时间语义**：采用 **event-time**；设置 `watermark_ms` 与 `reorder_drop_ms`；RTH/ETH 影响风控与撮合逻辑。

---

## 5. 数据层与存储

### 5.1 数据库分层

* **PostgreSQL（交易 OLTP）**

  * 表：`orders`（唯一 `idempotency_key`、`ib_perm_id`、状态与注释）、`fills`（唯一去重索引）、`positions`、`strategy_ledger`、`order_reservations`、`reconciliation_log`、`health`。
  * **PG Advisory Lock**：审批原子（策略或策略×标的）。
* **高频时序库**

  * 优先 **TimescaleDB**（落地快，PG 生态）存 `bars_5s/10s/1m` 与衍生特征；
  * 若 1s/tick 规模爆发，预留迁移 **ClickHouse** 接口。
* **Redis（缓存/限流）**

  * 活跃集合缓存、撤改速率计数、轻量延迟队列（非权威数据）。

### 5.2 聚合与回补

* 订阅 IB 5s RTBars，原样发布 5s；10s=2×5s 聚合；1m 聚合用于特征与慢环。
* 冷启动：拉取 `today-so-far 1m` 与必要的 `5s`；后台“修洞”并记录告警与降级状态。

---

## 6. 执行/止损与快环（5–10 秒）

### 6.1 快环职责

* **择时入场**：计划批准后在 5–10s 循环内确认（价带、点差、最小成交量、微动量/ATR），满足才下单。
* **止损与持盈**：三层止损（硬停/追踪/BE&Time）、Stop-Limit→市价升级、撤改节流、OCO 即时保护。
* **风控加速**：time-stop 秒级；灾难偏离（N×microATR）触发 flatten；流动性异常暂停新开仓。

### 6.2 策略差异化默认（示例）

| 策略             | 追踪系数 k1 (×ATR_micro) | MaxLoss% |      死区步进 | 最小改价间隔 |
| -------------- | -------------------: | -------: | --------: | -----: |
| ORB Retest     |              1.5–2.2 |  1.0–1.3 | ≥1–2 tick | 10–12s |
| Trend Pullback |              2.0–3.0 |  0.8–1.2 | ≥1–2 tick | 12–15s |
| VWAP Revert    |              1.2–1.8 |  0.7–1.0 | ≥1–2 tick | 10–12s |

> 实际参数放入 `param_registry`，可热更但受上下界约束。

## 7. 风控与资金（策略资金池、订单预留、板块暴露）

### 7.1 策略资金池（Strategy Ledger）

* 字段：`strategy_id, capital_limit_usd, reserved, realized_pnl, unrealized_pnl`。
* 不变式：`reserved ≤ capital_limit + realized + unrealized − margin_usage − buffer`。

### 7.2 订单级资金预留（Order Reservations）

* 下单审批通过 → 计算 `notional × (1 + buffer_bps) + fee_bps` 并**立即预留**；
* 订单终态（Filled/Cancelled/Rejected）→ **释放**；
* 预留与终态释放始终**强一致**（事务内 + 审计日志）。

### 7.3 集中度/板块暴露

* 行业映射（GICS/自定义）；阈值（%NAV 或 notional）；触发→拒单或缩量；可配置**优先级**与**处置策略**。

### 7.4 互斥/限速与暂停

* `symbol_exclusive`、撤改速率上限、最大并发订单数；
* 连续亏损暂停（lose-N-pause-Mmin）；时间窗与恢复条件。

## 8. 配置与参数管理（热更/守门/审计）

* **分层配置**：`engine/strategy/data/execution/risk/portfolio/reconcile/backtest/dashboard/ledger`；
* **param_registry**：为**可热更参数**设定上下界与步长；热更走**原子替换 + 版本戳**；交易时段内**仅允许收紧**类参数（安全）。
* **审计**：记录操作者、版本号、哈希、变更差异；一键回滚。

## 9. 可观测性与运维（SRE）

* **指标**：MicroBar 延迟、Kafka Lag、订单生命周期时延、OCO 挂载成功率、Stop-Limit→市价升级率、预留/释放平衡、对账动作数、IB 连接质量、DB 连接池水位。
* **日志/追踪**：事件 ID、`order_ref`、`idempotency_key`、`param_hash` 全链路透传。
* **健康探针**：交易前**Pre-flight Checks**（DB/IB/Kafka/时钟）；心跳丢失→**Kill-Switch**（只许平仓）。
* **告警**：无保护窗口、审批锁超时、预留失衡、修洞失败/降级、止损响应超时、Lag 超阈。
* **Runbook**：每类告警的定位→处置→回滚步骤；定期 GameDay 演练。
* **重放工具**：受控 Kafka 重放（影子环境），用于复盘与一致性测试。

## 10. 安全与合规

* **鉴权与 RBAC**：控制面写操作仅限授权用户；策略侧不可写 Control 主题。
* **密钥与凭据**：Vault/环境隔离；最小权限原则。
* **审计留痕**：控制命令、资金预留、审批拒单、熔断等关键动作都带审计记录。

## 11. 验收与里程碑（重写版）

**M1：基线可跑（2–3 周）**

* 引擎最小 API、数据服务（1m + 5s MicroBar）、执行服务（基本下单 + OCO 即时保护 + 巡检）、Portfolio 快照、Pre-flight 检查、Dashboard 只读、PG/TSDB 落库。
* 验收：小额灰度；OCO 漏挂=0；分钟完整≥99.9%。

**M2：风控与资金（1–2 周）**

* 策略资金池 + 订单预留 + PG 锁；集中度/板块暴露；lose-N-pause；控制台只读告警。
* 验收：并发压测不超限；预留与终态严格平衡。

**M3：快环与止损（1–2 周）**

* 5–10 秒择时、三层止损（含升级市价）、撤改节流；Meta-Order 基线（TWAP）。
* 验收：端到端延迟 P95≤500ms；Stop-Limit→市价升级率在阈内。

**M4：Reconciliation 2.0（1 周）**

* 孤儿/幽灵/重建 + 阈值 + 审计；冷启动≤5分钟。

**M5：回测一致性与重放（1–2 周）**

* 同构撮合（限价/滑点/拆单）、状态序列对齐测试；Kafka 受控重放（影子）。

**M6：可观测性完善与Runbook（1 周）**

* 仪表盘完整、告警分级、Kill-Switch、演练通过。

> 注：里程碑可并行推进；每阶段灰度上线、可回退。

# A. 数据与存储（ClickHouse 方案）

## A.1 流程总览

```
[IBKR TWS/ib_insync]
    └── tick (~250ms), realtimeBar(5s), hist(1m/5s)
         ↓
[Data Service]  → Kafka: md.tick.v2, md.bar.5s.v2, md.bar.1m.v2
         ↓                                   ↓
   (直推引擎内存)                     [ClickHouse Kafka Engine]
                                               ↓
                              Materialized View → MergeTree 事实表
                                               ↓
                               派生/聚合视图（5s→10s→1m）
```

* **实时**：Data Service 同步推送到**事件总线**（供引擎/策略用），同时**异步落地 CH**（Kafka Engine + 物化视图）。
* **历史/回补**：Data Service 用 IB 历史接口拉取 **today-so-far** 与缺口段，批量写 CH，再补发事件（带延迟标记 / replay 标志）。

## A.2 ClickHouse 表设计（初版）

> 命名规律：`md_*` 行情、`feat_*` 特征、`bar_*` K 线。日期分区，symbol 次级排序。

```sql
-- 1) Tick 级（最高 ~250ms）
CREATE TABLE md_tick_v2
(
  trade_date Date,
  ts DateTime64(6, 'UTC'),
  symbol LowCardinality(String),
  px Float64,
  qty UInt32,
  bid Float64, ask Float64, bid_sz UInt32, ask_sz UInt32,
  src LowCardinality(String),     -- IBKR
  event_id UUID,                  -- 去重/溯源
  part_key UInt32                 -- 分区辅助(可选)
)
ENGINE = ReplacingMergeTree(event_id)
PARTITION BY trade_date
ORDER BY (symbol, ts);

-- 2) 5s bar（流入：KafkaEngine→物化视图汇总）
CREATE TABLE bar_5s_v2
(
  trade_date Date,
  ts_start DateTime64(3, 'UTC'),  -- 窗口起点
  ts_end   DateTime64(3, 'UTC'),  -- 窗口终点
  symbol LowCardinality(String),
  open Float64, high Float64, low Float64, close Float64,
  vol UInt64,
  vwap Float64,
  rth UInt8                      -- 1=RTH, 0=ETH
)
ENGINE = MergeTree
PARTITION BY trade_date
ORDER BY (symbol, ts_start);

-- 3) 10s/1m bar 采用物化视图(建议)或离线批处理派生
CREATE TABLE bar_10s_v2  AS bar_5s_v2 ENGINE = MergeTree PARTITION BY trade_date ORDER BY (symbol, ts_start);
CREATE TABLE bar_1m_v2   AS bar_5s_v2 ENGINE = MergeTree PARTITION BY trade_date ORDER BY (symbol, ts_start);

-- 4) 预计算特征（日内可滚动/收市后快照）
CREATE TABLE feat_intraday_v2
(
  trade_date Date,
  ts DateTime64(3, 'UTC'),
  symbol LowCardinality(String),
  atr_1m Float64,
  vol_ma10 Float64,
  trend_slope_20 Float64,
  vwap_anchored Float64,
  calc_mode Enum8('realtime'=1, 'backfill'=2, 'postclose'=3),
  version UInt32                  -- 算法版本/参数版本
)
ENGINE = MergeTree
PARTITION BY trade_date
ORDER BY (symbol, ts);

CREATE TABLE feat_daily_snapshot_v2
(
  asof_date Date,
  symbol LowCardinality(String),
  params_hash FixedString(32),    -- 参数/窗口的哈希
  precomputed JSON,               -- 历史依赖型参数/分位/阈值等
  version UInt32
)
ENGINE = MergeTree
PARTITION BY asof_date
ORDER BY (symbol);
```

> 说明
>
> * Tick 用 **ReplacingMergeTree(event_id)** 去重；Bar 用 MergeTree（由物化视图聚合），避免行内更新。
> * 5s→10s/1m：用 **物化视图**或后台作业聚合；确保**窗口对齐**（UTC 边界、RTH 标记）。
> * 特征分两类：**intraday**（滚动）与 **daily_snapshot**（收市后一次性产物）。

## A.3 Kafka ↔ ClickHouse

* 为每个主题建立 **Kafka Engine 表** + 物化视图（MV）将原始事件写入 MergeTree 表：

  * `k_md_tick_v2` → MV → `md_tick_v2`
  * `k_md_bar_5s_v2` → MV → `bar_5s_v2`
* MV 中完成**字段映射、去重、类型清洗、RTH 标注**。
* 对 today-so-far 回补采用**批量插入**（避免与实时竞争），并在 `calc_mode='backfill'` 标记。

## A.4 抗抖动与乱序（Event-time）

* **乱序窗口（watermark）**：聚合窗口允许 **Δ=2s**（可配）迟到；迟到且越界的 tick 仅用于后续窗口，不回溯修改已落表 bar。
* **网络抖动缓冲**：Data Service 侧为 5s 窗口设置 **本地 200–400ms** 缓冲后再发 `bar_5s`（P95 控制），避免将短抖动放大。
* **去重策略**：用 `(event_id)` 去重；对于 IB 重发/重连，Data Service 在事件层保证 `idempotency_key` 稳定。
* **缺口修复**：后台对齐应有窗口 vs 实际窗口；发现缺口→发起 IB 历史拉取→补写到 CH，并标记 `calc_mode='backfill'`。

# B. 策略调度（5s 最小，可独立配置/智能跳过）

## B.1 运行时调度模型

* **Per-Strategy Runtime Scheduler**（每策略一个调度器）

  * 配置：`min_cadence_s`（最小间隔，默认 5s）、`default_cadence_s`（如 10s/20s/60s）、`max_cadence_s`、`adaptive=true/false`
  * **独立运行**，互不影响；可在 Dashboard 动态调参
  * **公平性**：全局 token-bucket 限流，避免同时爆发导致拥塞

* **触发条件（readiness predicate）**

  1. **时间**：距离上次执行 ≥ 当前 cadence
  2. **数据就绪**（任一不足则**智能跳过**本次）

     * 最近 N 根 `bar_5s/10s/1m` 连续完整（带 RTH 校验）
     * 所需特征（intraday 或 snapshot）在 CH 有**可用版本**
     * IB/执行/风控当前非降级（例如只许平仓模式）
  3. **策略自定义前置**（可选）：如最小成交量、点差上限

* **自适应 cadence（可选开启）**

  * **基于波动**：若 microATR/波动低于阈值，则将 cadence 拉长（如 5s→10s/20s），减少无效触发
  * **基于负载**：系统负载高时可全局上调 `min_cadence_s`（保底 5s）

## B.2 缺数据智能跳过（“跳过不减分”）

* 策略执行前检查**依赖数据**是否齐备：

  * **历史依赖**：直接从 `feat_daily_snapshot_v2` 读取（收市后产物）；
  * **日内依赖**：从 `bar_5s_v2 / bar_1m_v2 / feat_intraday_v2` 读取最近窗口；
* 缺任一关键数据 → **本次跳过**，记录 `skip_reason`（数据不足/窗口缺口/特征过旧等）；下次触发再尝试。

## B.3 策略配置示例（每策略独立）

```yaml
strategies:
  - id: "ORB_Retest_A"
    symbols: ["AAPL","MSFT"]
    cadence:
      min_s: 5
      default_s: 10
      adaptive: true
      max_s: 60
    deps:
      bars_5s: 12         # 至少最近 1 分钟
      bars_1m: 30         # 至少最近 30 分钟
      features:
        intraday: ["atr_1m","trend_slope_20"]
        snapshot: ["precomputed_quantiles","regime_tag"]
    skip_on_insufficient_data: true
```

# C. 离线预计算（收市后跑，开盘即用）

## C.1 Nightly Builder（Post-Close）

* **时间**：收市后 T+0（或凌晨 T+1）
* **输入**：CH 中的 `bar_1m_v2` + 历史 N 天数据
* **输出**：

  * `feat_daily_snapshot_v2`：策略所需**历史依赖型**特征/分位/阈值/回归系数/状态机初值，写入一条 JSON（带 `params_hash` 与 `version`）
  * 更新 `feat_intraday_v2` 中**跨日需要的滚动量**的**初值**（可选）

## C.2 使用方式

* 策略在 `Initialize()`：

  * 拉取 `feat_daily_snapshot_v2`（最近 `asof_date`）填充本地只读缓存
  * 将快照的 `params_hash` 纳入日志/事件（可追溯）

# F. 验收标准（本章节针对你刚定的目标）

1. **吞吐与时延**

   * Tick 写入 CH：P95 入库延迟 ≤ 200ms；5s bar 事件生成→入库：P95 ≤ 400ms
   * 决策端到端（5s MicroBar → 策略 Decide）：P95 ≤ 500ms

2. **智能跳过**

   * 缺少依赖数据时，策略不执行且记录 `skip_reason`；数据恢复后自动继续

3. **独立节奏**

   * 不同策略可独立设 `min/default/max`；Dashboard 可热更（受上下界）

4. **回补与抗抖动**

   * today-so-far 回填成功率 ≥ 99%；网络抖动导致的乱序在 watermark 内完全吸收，无回溯改写
   * 缺口发现→补写→下一次策略决策可见（可观测指标）

5. **离线预计算**

   * 收市后生成 `feat_daily_snapshot_v2`；开盘前可读；缺失时策略能降级（跳过或使用默认阈值）
