好，我们进入 **P8：容灾 & 高可用（Resilience & HA）**。
目标是：任何单点失败都只降级、不失控；重启后**自动恢复**到正确状态、不重复下单；全链路有**明确的健康度与拉闸规则**。以下规范直接可落地（不生成文件）。

---

# 0) 目标与退出标准

**目标**

* 每个核心进程都有**幂等检查点**与**自愈流程**（replay/reconcile/领养）。
* 系统级健康度→ **自动降级**（只减不增）、**自动拉闸**（全局断路器）已接好。
* 升级/回滚支持 **蓝绿切换** 与 **金丝雀**。
* “**一次失效不致命**、多次失效有**清晰的人机切换**”。

**P8 退出标准（全部满足=完成）**

1. 任意核心进程杀死后，**1 分钟内**自恢复；恢复后**状态一致**（无重复下单/重复入账）。
2. 聚合器断流 3 分钟后恢复，**无缺窗**（1s 回填补齐）、特征流自动追平。
3. 执行器重启后**领养**所有在挂单 & 保护腿，**OCO 不变量=0 违规**。
4. 账本（Portfolio/Ledger）重启后，从**快照+增量**回放，NAV/仓位连续无跳变。
5. 统一健康面板 + 告警规则生效，**Runbook 演练 6 条**全部通过（见文末）。

# 1) 组件清单与健康契约

核心进程（你现有模块对齐）：

* **Aggregator**（250ms/1s/5s 聚合、迟到修正、回填驱动）
* **Feature Engine**（增量特征、数据就绪门）
* **Strategy Scheduler**（每策略独立节奏触发 DSL）
* **Execution Engine**（下单、OCO、反手、重试；P6 已规范）
* **Portfolio Ledger**（fills→仓位/现金/NAV；P7）
* **AccountStateMonitor**（IBKR 账户/保证金；P4）
* **Reconciler**（启动/异常后的订单领养与幽灵清理；P6 有骨架）
* **System Manager**（守护/拉起/编排，已有 `system_manager.py`）

**每个进程必须对外暴露：**

* `liveness`（HTTP 200 或 statebus 心跳）
* `readiness`（“我能处理新工作”的条件：依赖全绿/积压<阈值/水位追平）
* `metrics`（Prometheus）
* `health_state`（OK / WARN / ERROR，带 TTL；写入 StateBus 的 `HEALTH::*`）

**统一影响表**

* `health_state != OK` → **策略端不新开**（只减不增）。
* `Aggregator/Feature` WARN/ERROR → `cadence` 自动放慢（x2/x4），或相应 symbol **跳过**。
* `Execution` WARN/ERROR → 禁新单 + 保护/撤单优先；
* `Portfolio` WARN/ERROR → 禁新单、继续消费 fills、优先对账；
* `AccountStateMonitor` WARN/ERROR → 启动 `PAUSE_NEW_ORDERS`（P4 已接）。

# 2) 检查点（Checkpoint）与回放（Replay）规范

| 模块                  | 检查点内容                                                           | 存储              | 回放规则                                               |
| ------------------- | --------------------------------------------------------------- | --------------- | -------------------------------------------------- |
| Aggregator          | `wm.last_seen_event_ts`、各频率`last_emitted_end`、`backfill_cursor` | Redis（热）+ CH（冷） | 从 `last_emitted_end` 往后重扫 1s bars；迟到修正用更大 `ver` 覆盖 |
| Feature             | 每 symbol 的 EMA/ATR/Z 分布状态（Welford/EMA 内部）                       | Redis（热）        | 从上次 5s 对齐时刻重算至当前；不足则“就绪门”跳过                        |
| Strategy Scheduler  | 每策略 `last_tick_ts`、`cadence_s`                                  | StateBus        | 恢复后先做“空跑检查”，不立即触发交易（见 §4）                          |
| Execution           | in-flight map（`idempotency_key→local state`）                    | PG（orders）为真源   | 重启不信内存，靠 Reconciler 从券商/PG恢复                       |
| Portfolio           | `positions_snapshot`（策略×标的） + `fills offset`                    | PG              | 先装快照，再从 `fills` 增量 offset 回放；最终与券商对齐               |
| AccountStateMonitor | 上次成功快照时间戳                                                       | PG              | 恢复即拉，连续失败≥3 推 `PAUSE_NEW_ORDERS`                   |

**Exactly-Once 约束**

* Kafka/队列消费：**仅提交**“本模块持久化成功后的 offset”。
* CH/PG 写：`ReplacingMergeTree(ver)`/唯一索引去重；失败不提交 offset。
* 所有跨进程 key（orders/fills/保护组）以 **PG 为真源**，Redis/内存为缓存。

# 3) 启停顺序与“冷启动护栏”

**启动顺序（建议）**

1. **AccountStateMonitor → Portfolio Ledger → Aggregator → Feature**
2. **Strategy Scheduler（只读/空跑态）**
3. **Execution Engine（断路器 L1 打开）**
4. **Reconciler**：收编在挂，修复 OCO；
5. **解除断路器 L1**，进入正常交易。

**空跑态（dry start）**

* Scheduler 在首个 `cadence` 间隔只做**规则评估**与**日志**，不发意图；
* 若 1 分钟内健康全绿且 Reconciler 完成，才允许发意图；否则维持空跑态。

**停机流程**

* 置断路器 L1（禁新单）；
* 等待 Execution 空闲（在挂清 0 或超时强撤）；
* 停 Scheduler→Feature→Aggregator→Ledger→Account→Reconciler；
* 最后停 System Manager / Dashboard。

---

# 4) Reconciler（领养 & 幽灵清理）细则

**输入**：券商 `open_orders()`、历史执行（可选）、PG `orders/fills`。
**匹配优先级**：

1. `orderRef == idempotency_key`（精确）
2. `symbol/side/price≈/qty≈/创建窗`（模糊，阈值：±1 tick、±5% qty、±5 分钟）

**处理动作**：

* 本地无、券商有 → **创建本地 shadow 订单**，state=ACK/PARTIAL；
* 本地有、券商无、未终态 → 标记 `STALE_CLOSED`；
* OCO 缺腿/错腿 → 5 秒内重建（3 次失败→KillSwitch 该策略）。

**守恒校验**（任一失败→报警/阻断新单）：

* `abs(保护腿数量 - abs(pos_qty)) == 0`
* `∑fills(order)=orders.filled_qty`
* `仓位=∑(方向×成交量)`

# 5) System Manager（守护/编排）规范

**职责**

* 启停顺序编排（§3）；
* 崩溃重拉（指数退避 1s,2s,4s…≤ 60s）；
* 注册心跳：每 2s 写 `HEARTBEAT::<service>` 到 StateBus；
* **阈值升级**：同一进程 5 分钟内失败≥N 次 → 置系统级 `DEGRADED`，自动断路器 L1。

**配置热加载**

* 参数变更（cadence/caps/风险阈值） → **分层生效**：先策略级→再全局；
* 变更签名（param_hash）写入 StateBus 与 CH 审计表。

**pacing/限流**

* Execution 侧**每策略** `pacing_ms`，超限进入排队；
* Aggregator/Feature 控制 `max_batch_ms / size`，防止 CPU 峰值。

# 6) 灾备（备份/恢复）

**PostgreSQL**

* PITR（WAL）开启；`orders/fills/positions_snapshot/cash_events/breaker_*` 全库日备。
* 恢复演练：在影子环境恢复到 T-1 12:00，重跑 Ledger 到 T-1 收盘，检查 NAV 一致。

**ClickHouse**

* 表均启用 `ORDER BY` & 合理 `PARTITION`；
* 每日 `BACKUP TABLE ... TO S3('bucket/...')`；
* 恢复靠 `RESTORE ...`；MV 允许重建。

**Redis**

* RDB 每 5 分钟，AOF yes；可选主从；
* 断电恢复后允许“**状态非权威**”，靠 CH/PG 重建（Aggregator/Feature 自愈）。

# 7) 监控 & 告警（统一指标）

**健康**

* `service_health{svc} ∈ {0,1,2}`（OK/WARN/ERROR）
* `heartbeat_age_s{svc}` < 10s
* `restart_count{svc}` 增长→WARN

**积压与延迟**

* `kafka_consumer_lag{topic,group}`
* `bars_emit_lag_ms_p99`、`features_emit_lag_ms_p99`
* `strategy_cadence_jitter_ms_p95`（> cadence*0.5→WARN）

**一致性**

* `oco_invariant_breaks_total`（=0）
* `reconcile_orphans_adopted_total`、`reconcile_ghosts_closed_total`
* `portfolio_ledger_lag_s` < 1.0

**断路器**

* `breaker_level{scope}`、`breaker_transitions_total{level}`
* `rejects_breaker_total / rejects_account_cap_total`

**资源**

* CPU/Mem/FD 打点（进程维度）
* IBKR 调用错误率、限流命中率

# 8) 部署与变更策略

**蓝绿发布（同机或同集群）**

* 新版以不同 `consumer group` 订阅（影子模式）→比对指标/日志；
* 交换入口（statebus 标志 or 反向代理 switch）；
* 失败 1 分钟内回切；保留旧版 24 小时。

**金丝雀**

* 1 个策略 / 3–5 个标的先切新版执行/账本；
* 告警宽松阈值 1 天，次日收紧。

**配置变更**

* 所有高风险参数（断路器阈值、价格带、caps）走“**两人复核**+ 10 分钟延迟生效**”。

---

# 9) 安全与时间

* **时间同步**：chrony，RMS < 50ms；超限→系统 WARN、禁新单。
* **凭据**：IBKR/TLS/DB 凭据用环境密钥或 Vault；轮换有审计。
* **最小权限**：执行器仅能写 `orders`、读 `caps`；策略仅读 `features/portfolio`。

---

# 10) Chaos/Runbook（演练 6 条）

1. **Aggregator 进程崩溃**：杀死→30s 内恢复；`bars_emit_lag_p99 < 1500ms` 5 分钟内回到绿区；缺窗 0。
2. **Feature 延迟上升**：限 CPU → 观察策略自动 `skip` 与 cadence 降档；解除后自动恢复。
3. **Execution 崩溃**：有 3 笔在挂+部分成交；重启后领养成功，不重复下单，OCO 0 违规。
4. **Portfolio 停机**：停 2 分钟→恢复回放后 NAV 连续；fills 无重复入账。
5. **IBKR 断连**：AccountStateMonitor 连续失败→ `PAUSE_NEW_ORDERS` 生效；恢复 5 分钟后解封。
6. **单机重启**（整个进程组）：按启动顺序恢复；系统 5–10 分钟内回正；期间禁止新单但允许减仓/保护。
