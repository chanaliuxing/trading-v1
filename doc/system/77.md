好，进入 **P9：多策略·多资金池（动态配额 & 自适应风控）**。
这一阶段把“每个策略独立资金池、独立节奏、互不干扰”落到**可计算、可审计、可回放**的调度系统里：账户→行业→策略→标的四级配额，配合**实时绩效/风险信号**做自适应分配与拥塞控制。以下是**一次成型的实现规范**（直接可用，不生成文件）。

# 0) 目标与退出标准

**目标**

* 账户级可用资金（P4）在不变前提下，**层级配额**：Account → Sector → Strategy → Symbol。
* **每策略独立资金池**（可设最小/最大/弹性区间），支持**多层级档位**与**动态降档/升档**。
* **实时调度**：基于 rolling 绩效（命中率、回撤、单位风险收益）与系统健康（延迟、拒单率）。
* **公平与效率**：拥塞时保证**公平最低配额**，在“有边际收益”的策略上**优先倾斜**。
* **Admission Controller** 在风控前门之前决定**是否放行/限流/延迟/降价**，并写**审计**。

**P9 退出标准**

1. 高峰拥塞期，**各策略最低配额均满足**；总资金使用不越过账户可用资金；
2. 动态降档/升档**实时可见**（面板），与回撤/拒单/延迟指标的阈值规则一致；
3. 任意 2 个高相关策略在同一标的上不会**双重加仓**（符号级限额生效）；
4. 配额调整事件 **Exactly-once**（PG 真源，StateBus 广播，策略接入生效<1s）；
5. A/B 演练：在 3–5 个策略上模拟拥塞，**总成交效率提升**、**坏策略被抑制**，有审计可复盘。

# 1) 结构与职责

```
Account (P4 available_cap)
  └─ SectorQuotaManager（行业/板块限额）
      └─ StrategyQuotaManager（策略资金池 + 档位/曲线）
          └─ SymbolLimiter（策略×标的 限额）
              └─ Admission Controller（入场：放行/延迟/丢弃/改价）
```

* **Capital Orchestrator**（新进程，或并入 RiskService）

  * 汇总实时：账户可用资金（P4）、Portfolio 暴露度（P7）、策略绩效、系统健康（P8）。
  * 每 **5s** 计算新配额；越权变更写 PG 并广播 StateBus。
* **Admission Controller**（执行器前一跳）

  * 基于“当前配额 + 本单需求 + 优先级/成本函数”决定去留。
  * 不通过时的动作：`reject | delay | clip_qty | reprice`（可组合）。

# 3) 动态配额算法（公平 + 效用最大化）

把策略视为“消费者”，资金视为“带宽”。
我们采用**“带最小保障的加权公平分享 + 效用倾斜”**：

## 3.1 变量

* `A`：账户可用资金（P4 `available_cap`）；
* `S`：策略集合，`i ∈ S`；
* `m_i`：策略 `i` 的**最小保障**（`cap_min`）；
* `M_i`：上限（`cap_max`，缺省=+∞）；
* `w_i`：权重（由 `priority`、`elast_mult`、`util_score_i` 计算）；
* `U_i(x)`：策略 `i` 的效用函数，默认 `U_i'(x) ~ diminishing`（边际递减）。

## 3.2 步骤

1. **先保障**：

   * 若 `Σ m_i > A` → 按 `priority` 与历史稳定性**比例缩放**至刚好等于 `A`。
   * 否则分配 `m_i`，剩余 `R = A - Σ m_i`。

2. **再分享**（加权最大化）：

   * 目标：分配 `r_i ≥ 0`，使 `Σ r_i = R`，并最大化 `Σ w_i · log(m_i + r_i)`（或其它 concave U）。
   * 解析解：`r_i = max(0, min(M_i - m_i, k·w_i - m_i))`，`k` 由 `Σ min(...) = R` 求得。
   * 实现：二分 `k`，复杂度 O(|S| log A)。

3. **行业/板块约束**（投影）：

   * 若某行业 `sector` 上汇总 `alloc_s` 超过 `cap_max(sector)` → 在该行业内再次做一次步骤 2 的“二次水位”重分配（只影响涉事策略）。

4. **效用权重 w_i 计算**（每 1–5 分钟更新一次）

   ```
   perf_i = clamp( z(Sharpe_60m) + 0.5*z(HitRate_60m) - z(DD_day),  -2, 2 )
   health_i = 1 - clamp(reject_rate_5m / 0.02, 0, 1)   # 拒单率>2%则惩罚
   latency_i = 1 - clamp(exec_p95_ms / 1500, 0, 1)
   w_i = base_weight(priority) * elast_mult * σ(perf_i) * health_i * latency_i
   ```

   * `σ` 为 Sigmoid，使极端绩效不会完全压制其他策略。
   * **冷却**：升档/降档后 `w_i` 在 `cooldown` 窗口内最多变化 ±20%。

# 4) 策略档位（Tier）与自动升降

**档位 L0..L4**（示例）

* L0：冻结（仅减不增）
* L1：保守（`alloc ≤ 0.25 * base_cap`）
* L2：常规（`alloc ≤ 1.0 * base_cap`）
* L3：进取（`alloc ≤ 1.5 * base_cap`）
* L4：激进（`alloc ≤ 2.0 * base_cap`）

**升降条件（样例，写入 `tier_rules`）**

```json
{
  "up":   {"sharpe_60m": 1.0, "hitrate_60m": 0.55, "dd_day": 0.005, "cooldown_min": 20},
  "down": {"dd_day": 0.01, "reject_rate_5m": 0.02, "breaker_hits_30m": 3, "cooldown_min": 10}
}
```

* 达到 `up` 条件 `cooldown` 后升一级；触发 `down` 条件立即降一级并启动冷却。
* 档位改变时，更新 `cap_max = tier_multiplier * base_cap`；写 `quota_events` 审计。

# 5) 符号/行业冲突与相关性抑制

**冲突情形**：两个策略同时在同一标的**同向**加仓，或相关性极高的标的（同一行业/ETF成分）在同方向拥挤。

**约束手段**

1. **SymbolLimiter（策略×标的）**：

   * `notional_max` + `daily_turnover_max`；超限→Admission Controller **clip_qty 或 delay**。
2. **Cross-Strategy Symbol Cap（全局）**：

   * `symbol_total_max`（账户级或行业级）；在 Admission 时做“剩余额度切分”。
3. **相关性惩罚**：

   * 对相关度高（ρ>0.8）的策略对，在同方向时对 `w_i` 乘以 `(1-ρ*α)`，降低倾斜。
   * ρ 基于近 60m 收益/因子相似度，CH 定期计算缓存。

# 6) Admission Controller（入场裁决）

**输入**：OrderRequest（P6）、当前配额快照、策略使用率、行业/标的占用、系统健康。
**输出动作**：

* `ACCEPT`：放行；
* `CLIP(qty')`：削减数量至剩余额度；
* `DELAY(dt)`：排队等待（带最大排队 TTL）；
* `REPRICE(px')`：价格带护栏调整（与 P6 Reg-Lite 联动）；
* `REJECT(reason)`：不满足硬约束。

**决策顺序**

1. **硬约束**：Breaker≥1、账户 `available_cap`、合规停牌/SSR/LULD → `REJECT`；
2. **行业/标的限额**：若超限 → `CLIP` 或 `DELAY`（如剩余额度将在 N 秒内释放）；
3. **策略额度**：若 `used ≥ alloc`：

   * 有“**突发信用**（Burst Credits）”→ 允许短时超用（见下）；
   * 否则 `DELAY/REJECT`（基于优先级）。
4. **价格护栏**：越带 → `REPRICE` 或 `REJECT`。
5. **节奏**：策略排队/`pacing_ms` 未满足 → `DELAY`。

**Burst Credits（可选）**

* 按策略给定 `burst_tokens`（名义金额），**滑动/漏桶**回补；
* Admission 时可透支；超时未回补 → 自动降档或冻结。

# 7) 实时循环（Orchestrator）伪码

```python
async def quota_loop():
    while True:
        A = account.available_cap()                      # P4
        usage = portfolio.usage_by_strategy()            # P7 used_cap
        perf = metrics.strategy_perf_rolling()           # sharpe/hitrate/dd
        health = metrics.system_health()                 # reject/latency/lag
        sectors = sector_usage_and_caps()                # 当前行业占用/上限

        # 1) 计算 w_i（有冷却/钳位）
        w = compute_weights(perf, health, base_prio, elast_mult, cooldowns)

        # 2) 先保障 cap_min，再公平分享（二分水位）
        alloc = fair_share(A, cap_min, cap_max, w)

        # 3) 行业投影：每个 sector 超限时二次分配
        for sec in sectors:
            alloc = project_to_sector(alloc, sec.cap_max, sec.members)

        # 4) 档位升降（基于 perf/health + cooldown）
        new_tiers = update_tiers(perf, rules, cooldown_state)
        apply_tiers(alloc, new_tiers)

        # 5) 落库+广播
        await pg.upsert_strategy_alloc(alloc, new_tiers)
        await statebus.publish("QUOTA_UPDATE", snapshot(alloc))
        await ch.append("strategy_quota_5s", alloc_to_rows(alloc))

        await asyncio.sleep(5)    # 5s 周期
```

**Admission 侧使用**

```python
def admit(order_req):
    sid = order_req.strategy_id
    need = notional(order_req)
    alloc = cache.alloc[sid]; used = cache.used[sid]

    if breaker.level>=1 and is_open_increase(order_req):
        return REJECT("breaker")

    if used + need <= alloc: 
        return ACCEPT()

    if burst.can_borrow(sid, need):
        burst.consume(sid, need); return ACCEPT()

    if alloc - used > min_lot_notional:
        clipped = clip(order_req, alloc - used)
        return CLIP(clipped)

    if queue.can_wait(sid):
        return DELAY(eta=queue.eta(sid))

    return REJECT("over_alloc")
```

# 8) 监控 & 告警

* **配额**：`strategy_alloc / used / headroom`（剩余额度）
* **公平性**：`cap_min_satisfied_ratio`（满足最小保障的策略比例）> 95%
* **效用**：`util_score` 分布与漂移；`w_i` 波动（冷却期内不应>20%）
* **Admission 结果**：`admit_accept/clip/delay/reject_total{reason}`
* **行业限额**：`sector_usage_ratio{sector}` > 0.9 告警；>1.0 红牌
* **拥塞**：`queue_len{strategy}`、`delay_ms_p95`
* **突发信用**：`burst_outstanding{strategy}` 长时间>0 → 降档警示

# 9) 演练与验收（60–90 分钟）

1. **拥塞公平**：三策略同时请求>账户资金；验证每个策略至少拿到 `cap_min`，剩余按权重分配。
2. **效用倾斜**：人为提高 A 策略 `Sharpe_60m`，观察其 `alloc` 上升；同时 B 策略拒单率升高→`alloc` 下调。
3. **行业上限**：设置 TECH 行业上限，两个策略在 TECH 加仓→二次分配生效，总占用不越界。
4. **同标的冲突**：两个策略同时对 AAPL 同向加仓→SymbolLimiter 生效：`clip/delay` 正常。
5. **档位升降**：注入回撤→策略降档；冷却期内禁止升档；冷却结束后绩效改善→自动升档。
6. **突发信用**：给某策略开 `burst_tokens`，短时透支后 30s 内补回；若未补回→自动降档。

# 10) 与现有阶段的接口

* **P4**：账户 `available_cap` 是**硬顶**；Orchestrator 内把 `A` 设为 `available_cap` 的安全折扣（如 ×0.98）。
* **P6**：Admission Controller 在 `approve_and_reserve()` 之前决策；结果写统一审计（与 P6 拒单码对齐）。
* **P7**：`used_cap` 与名义暴露来自 Portfolio（仓位）+ Reservation（在挂）；Orchestrator 定期读。
* **P5**：系统延迟/滞后指标（bars/features lag）参与 `w_i` 惩罚，避免“数据慢但拼命下单”的策略。
* **P8**：当模块 `health_state!=OK` → Orchestrator 自动把相关策略 `alloc=cap_min`（或 L0）。

# 11) 风险与反模式

* **过度频繁调整**：配额频繁抖动会导致策略行为不稳定——使用**冷却/钳位**（每次±20%）。
* **绩效漂移误判**：短窗指标易噪声过拟合——指标用 EWMA + zscore + 上下限（[-2,2]）。
* **相关性未控制**：同方向相关策略叠加风控必须用行业/相关性惩罚，否则系统整体回撤扩大。
* **突发信用滥用**：Burst 只能应对短时机会，不可长期“借新补旧”；未归还即降档或冻结。
* **黑箱化**：所有配额变更必须**可审计**（`quota_events`），面板展示“为什么被限/被加”。
