# 0. 总览（事件优先，REST/gRPC 只做运维与调试）

* **业务主线：Kafka 事件合约**（强幂等 + 可回放）

  * `md.*`：行情（tick/5s/1m）——已定
  * `engine.*`：策略发单意图
  * `risk.*`：审批与资金预留决定
  * `exec.*`：下单状态与成交
  * `portfolio.*`：仓位/PnL 快照
  * `control.*` & `health.*`：控制与健康
* **控制面：FastAPI（RBAC + 审计）**

  * 只读：状态/指标/缺口
  * 有权写：Halt/Resume、策略节奏热更、手动回补、风险限额调整（走守门）
* **关系数据库（PG）与 CH 已按前文落地**：本规范只定义“线上的合约”。

# 1. 事件主题与消息体（JSONEachRow）

## 1.1 策略下单意图（Engine → Risk）

**Topic**：`engine.order.request.v2`
**Key**：`{strategy_id}:{symbol}`
**Value**

```json
{
  "schema_v": 2,
  "metadata": {
    "event_id": "uuid",
    "ts_us": 1730541234567890,
    "producer": "engine",
    "idempotency_key": "ord:req:{strategy_id}:{symbol}:{uid}",
    "correlation_id": "uuid"          // 一路透传到 status/fill
  },
  "data": {
    "strategy_id": "ORB_A",
    "symbol": "AAPL",
    "side": "BUY",                     // BUY/SELL
    "order_type": "LMT",               // MKT/LMT/STP/STP_LMT
    "qty": 100,
    "limit_px": 221.35,                // LMT/STP_LMT需要
    "stop_px": null,                   // STP/STP_LMT需要
    "tif": "DAY",
    "notional_hint_usd": 22135.0,      // 风控预留用（必填）
    "slippage_buffer_bps": 8,          // 建议缓冲（可由风控覆盖）
    "time_stop_s": 900,                // 可选
    "tags": ["entry","alpha:orb","cadence:5s"],
    "params_hash": "…",                // 策略参数哈希
    "notes": "optional"
  }
}
```

> 语义
>
> * **幂等**：同 `idempotency_key` 的请求只能被审批一次；执行只创建一笔订单。
> * **notional_hint_usd** 用于**资金预留**，结合缓冲 bps 计算 `reserved_usd`。
> * **correlation_id** 全链路打通日志/追踪。

# 2. 执行器：OCO/止损参数体系（param model）

## 2.1 结构（可由策略或全局覆盖）

```json
{
  "stop": {
    "hard_kill_pct": 1.5,             // 灾难硬停：相对入场的不利移动%
    "trailing": {
      "atr_source": "microATR_5s|ATR_1m",
      "atr_k": 2.0,                    // 追踪距离 = k * ATR
      "min_step_ticks": 1,             // 最小改价步
      "min_modify_secs": 12,           // 最小改价间隔
      "max_updates_per_min": 6         // 撤改节流
    },
    "time_stop_s": 900,                // 到时平
    "breakeven": {
      "enable": true,
      "trigger_rr": 1.0,               // 到 R=1 提价到 BE
      "tighten_rr": 2.0                // 到 R=2 收紧trailing（atr_k 下降）
    }
  },
  "take_profit": {
    "mode": "ratio|px|disabled",
    "rr": 2.5,                         // R 倍或
    "px": null                         // 指定价格
  },
  "oco": {
    "place_after_first_fill": true,    // 首填即挂
    "cancel_peer_on_fill": true,
    "inspection_secs": 5               // 巡检间隔，保障双保护
  }
}
```

**修改规则**

* 交易时段内支持**只收紧**（例如减小 `atr_k`、缩短 `time_stop_s`），放松需要暂停策略后生效。
* `min_modify_secs` / `max_updates_per_min` 为**硬护栏**（执行器强制执行）。
* **OCO 挂载失败** → 立即重试；重试仍失败 → **升级到 Stop-MKT** 并报警（Kill-Switch 观察项）。

# 3. Risk/Exec 服务 API（可选 REST/gRPC，用于调试/回放）

> 生产以**事件**为准；下面接口用于**单测、压测、回放**或**运维**。

## 3.1 Risk REST

* `POST /risk/approve`
  **Body**：与 `engine.order.request.v2.data` 一致 + `idempotency_key`
  **200**：`{status:"APPROVED|DENIED|RETRY_LATER", reservation_id?, reserved_usd?, reason?}`
  **语义**：内部调用 `core_sp_risk_approve_and_reserve()`；**强幂等**。

* `POST /risk/release`
  **Body**：`{idempotency_key, order_id?, terminal:"FILLED|CANCELLED|REJECTED", reason}`
  **200**：`{ok:true, released_usd}`
  **语义**：内部调用 `core_sp_release_on_terminal()`。

## 3.2 Exec REST

* `POST /exec/order`（仅影子/回放）
  **Body**：`{idempotency_key, approved_decision, broker_route_hint?}`
  **行为**：幂等写 `core_order`，模拟提交。

* `POST /exec/oco/inspect`
  **Body**：`{strategy_id, symbol}`
  **200**：`{ok:true, details:[{order_id, type, px, qty, state}]}`
  **语义**：巡检 OCO 是否“双全”。

# 4. 对账恢复 2.0（匹配与回滚，SQL 草案）

## 4.1 匹配顺序

1. **permId 精确**

```sql
SELECT o.order_id FROM core_order o WHERE o.ib_perm_id = :perm LIMIT 1;
```

2. **orderRef 半精确**

```sql
SELECT o.order_id FROM core_order o
WHERE o.order_ref = :orderRef AND o.symbol = :symbol
  AND o.state IN ('SUBMITTED','PARTIAL') LIMIT 1;
```

3. **模糊匹配（合约+方向+价差≤bps+时间窗）**

```sql
SELECT o.order_id
FROM core_order o
WHERE o.symbol = :symbol AND o.side = :side
  AND o.state IN ('SUBMITTED','PARTIAL')
  AND ABS((o.limit_px - :broker_px)/:broker_px) * 10000 <= :tolerance_bps
  AND o.submitted_at >= now() - INTERVAL ':adopt_window_min minutes'
ORDER BY ABS(o.limit_px - :broker_px) ASC
LIMIT 1;
```

## 4.2 领养/清理动作

* **领养**：写回 `ib_perm_id / broker_order_id / oca_group`；若缺 OCO → 立刻补挂（止损至少为 Stop-MKT）。
* **清理**：`DB 有、IB 无` 的活跃单 → `state='CANCELLED'` + `core_reconcile_log`。
* **最大动作数**：`max_actions_on_start`（例如 500），超过则**分批**执行，避免风暴。
* **失败回滚**：任何领养/清理出现异常 → 该批次**标记 FAILED**，人工介入（不继续自动动作）。

# 5. 控制面（关键写接口 + 审计 + RBAC）

* `POST /control/halt` → `trading_mode='FLATTEN_ONLY'`（全局只许平仓）
* `POST /control/resume`（需要观察期，确认健康指标恢复）
* `POST /strategies/{id}/cadence`（热更 min/default/max/adaptive，走参数守门）
* `POST /data/backfill`（symbol+时间窗，异步任务）
* `POST /risk/limit/{strategy}`（调整策略资金上限，需二次确认 & 审计）

**审计统一字段**：`actor, role, ts, ip, payload_hash, result, reason?`

# 6. 监控与告警（与前文指标合并，新增几项）

* `order.oco_attach_success_rate == 1.0`（告警：<0.995）
* `order.unprotected_window_seconds == 0`（>0 立刻红警 + 触发观察 Kill-Switch）
* `risk.reservation_mismatch_usd == 0`（账不黑）
* `reconcile.restore_time_seconds <= 300`
* `strategy.skips_total{reason="DATA_GAP_5S"}` 上升速率阈值（说明数据面异常）
* `exec.stop_to_market_upgrade_total`（监控极端行情下的升级频次）

# 7. 验收用例（黑/白盒）

* **幂等串测**：同 `idemp_key` 的请求 → 只产生 1 个 reservation、1 个订单、1 次释放。
* **并发冲关**：同 `strategy×symbol` 并发 10 个请求 → 仅 1 个被批准，其余 `RETRY_LATER/LOCKED`。
* **OCO 巡检**：首填后 ≤1s 内必出现 OCO；主动删掉一边 → 巡检 5s 内补齐。
* **Reconcile 全真**：启动时 IB 有 50 个实挂单（含部成/有 OCO/无 OCO） → 5 分钟内全部领养/清理，仓位/OCO 一致。
* **Kill-Switch**：中断 IB/Kafka/CH 各 5 分钟 → 系统进入只平仓；恢复后需要人工解除。
* **策略独立节奏**：两个策略同一 symbol，分别 5s/20s 节奏，skip/execute 互不影响。

## 收尾

* 这套**统一合约 v1.0**与我们已定的 **ClickHouse（tick/5s/1m）**、**5s 独立调度**、**PG 资金预留**、**OCO 三层止损**、**对账 2.0** 完全对齐。
* 工程可以据此同时开工：

  * 引擎输出 `engine.order.request.v2`；
  * 风控按合约返回 `risk.decision.v2` 并落 PG；
  * 执行消费 `APPROVED`、输出 `status/fill` 并保证 OCO；
  * 组合消费 `fill` 维护权威仓位；
  * 控制面挂上 RBAC/审计与关键 SLO。
