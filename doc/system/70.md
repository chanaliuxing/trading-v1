## 1) 端到端接线顺序（事件 → 幂等加工 → 落地 → 水位对齐 → 快照）

**事件源（二选一或并行）**

1. `events.fills.v1`（Kafka，来自执行器/IB 回报）
2. `fills`（PostgreSQL 实时入库的成交表）

**账本作业（Python，单进程/多分区消费者）**
3. 消费 1 或轮询 2 → 规范化为 `fill`（必含：`strategy_id,symbol,side,qty,price,fee,ts,order_id,decision_id,param_hash`）
4. 生成 **幂等键** `fill_uid`（详见 §2），并**去抖动/按 ts 排序**（同分区内）
5. 读取/维护**内存状态**（每 `(strategy_id,symbol)` 一个 `Lot{pos,avg,cash}`）
6. 调用递推：`step_fill()` → 得到 `pos_after, avg_after, realized_delta, cash_after`
7. **批量写 CH**：

* `pnl_fills`（逐笔账本）——带 `fill_uid, ver, ingest_ts`
* 维护“最后一条 bar 的 `ts_end`”水位，踩到新 5s 窗口→写 `pnl_pos_5s` 快照

8. **提交偏移量**：Kafka 场景下，**仅在写入成功后**提交 offset；PG 场景下记录“已处理的 `max(ts,fill_uid)` 游标”。

---

## 2) 幂等键设计（Exactly-Once 的核心）

**优先级生成规则（取能拿到的最强标识）：**

1. `fill_uid = ib_exec_id`（IBKR 提供的逐笔 `execId`）
2. 否则：`fill_uid = sha1(f"{account}|{order_id}|{ts_ms}|{side}|{abs(qty)}|{round(price,5)}")[:20]`

   * 同一笔成交的重复投递 → `fill_uid` 完全一致
   * 将 `fill_uid` **写入 CH**，并作为 **ReplacingMergeTree 的排序键之一**（保证重复 INSERT 只留最新）

**Version（`ver`）**

* 取 `toUInt64(now64())` 或 `logical_seq`；同一 `fill_uid` 多次写入 → `ver` 更大的**覆盖旧行**。
* 对 `pnl_pos_5s` 亦使用 `ReplacingMergeTree(ver)`，键为 `(strategy_id,symbol,ts_end)`。

**错误处理与退避**

* CH 写入失败 → **不提交 offset**，指数退避重试；
* 单行异常（字段缺失等）→ 写入 **DLQ 主题** `events.fills.dlq.v1`；
* Kafka 暂时不可用 → 暂停消费，健康探针报警；
* 账本进程崩溃重启 → 依赖 Kafka offset，**从最近已提交位置恢复**；状态 `Lot` 会在重放时被**正确复建**（因逐笔递推是纯函数且幂等）。

## 5) 回放/回补与“检查点”策略

**为什么要检查点？**

* 一天成交很多时，重算从零开始成本高；
* 我们维护**可选的** `pnl_ckpt`（每 `(strategy_id,symbol)` 每小时或每 N 笔）**快照**，中断/回补时从最近检查点重放。

**最小快照表（可选）**

```sql
CREATE TABLE pnl_ckpt (
  strategy_id LowCardinality(String),
  symbol      LowCardinality(String),
  ts_ckpt     DateTime64(3),
  pos         Int64,
  avg         Float64,
  cash        Float64,
  ver         UInt64
)
ENGINE = ReplacingMergeTree(ver)
ORDER BY (strategy_id, symbol, ts_ckpt)
PARTITION BY toDate(ts_ckpt);
```

**回补流程**

1. 将历史 fills（或修正）写入源头（Kafka/PG）→ 带相同或更高 `ver`；
2. 触发“区间重算”作业：

   * 读取该 `(strategy_id,symbol)` 在回补区间起点**之前**最近的 `pnl_ckpt`；
   * 清理 CH 中该区间的 `pnl_fills/pnl_pos_5s`（或直接覆盖写入更高 `ver`）；
   * 从检查点开始重放 fills → 重写两张表；
3. 报表端读取 `FINAL` 或 `max(ver)` 即见新结果，无需停机。

## 6) 失败重试矩阵（运营态必须遵守）

| 故障          | 症状                        | 行为                          | 保障                                |
| ----------- | ------------------------- | --------------------------- | --------------------------------- |
| Kafka 暂停/超时 | `consumer.poll` 超时、lag 上升 | 暂停 flush，重试；不提交 offset      | **不丢单**（偏移未提交）                    |
| CH 写入失败     | HTTP 5xx / 超时             | 整批重试（退避）；超过 N 次→写入 DLQ 并报警  | **至少一次投递 + 幂等**（`fill_uid`+`ver`） |
| 单行坏数据       | 反序列化/字段缺                  | 跳过此行，写 DLQ（原始 payload + 错误） | **不阻塞批**，可线下回补                    |
| 账本进程崩溃      | 进程退出                      | 重启后从**最后提交 offset**恢复；逐笔重放  | **状态可重建**                         |
| 回补穿越检查点     | 回补 ts < ckpt              | 区间重算，从最近 ckpt 重播            | **最终一致**                          |
| 重复/乱序投递     | 同笔 fill 多次/跨分区            | 幂等键使重复合并；递推按 ts 排序处理        | **Exactly-Once 效果**               |

## 8) 金丝雀发布建议（账本作业自身）

* **分区数**：初期 1–2 分区（按策略或按 symbol hash），避免乱序；
* **幂等演练**：人工重复投递同一 fill（相同 `fill_uid`）×10 次 → `pnl_fills` 行数不增长；
* **断点恢复演练**：拉闸退出 → 启动后从断点继续，`pnl_pos_5s` 连续无跳变；
* **回补演练**：插入一段历史 fills → 触发“区间重算”，报表正确覆盖。

* 通过 **`fill_uid` + `ReplacingMergeTree(ver)` + “提交后再提交偏移量”**，我们在 Kafka→账本→CH 链路上实现了**幂等 + 至少一次**的组合，从而达到**Exactly-Once 的可感知效果**；
* 结合检查点与区间重算，**回补/修正**不需要停机；
