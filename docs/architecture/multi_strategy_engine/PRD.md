# PRD: Generalized Multi-Strategy Execution Engine

## 1. Context
Current system already supports multiple strategy IDs in core engine, and has staged netted execution components. We need production-grade generalization and traceability before integrating new execution-layer changes into `run_system`.

## 2. Problem Statement
When multiple strategies trade the same symbol, ownership and causality can become ambiguous at broker and reconciliation layers. We need auditable, isolated, and replayable execution behavior.

## 3. Product Goals
- G1: Run N strategies concurrently, including same symbol overlap.
- G2: Support N strategies on same symbol without cross-strategy state bleed.
- G3: Provide order lineage answer within seconds:
  - "At time T, which strategy and which trigger generated this order?"
- G4: Roll out with zero regression to daily `run_system` baseline until explicitly enabled.

## 4. Non-Goals
- No immediate replacement of all legacy strategy code paths.
- No forced migration of every old log key on day one.
- No mandatory netting for all symbols/strategies.

## 5. Personas
- Operator: needs incident-grade traceability.
- Strategy developer: needs isolated behavior and deterministic replay.
- Risk reviewer: needs proof that each order has accountable owner and trigger.

## 6. Functional Requirements
- FR1: Every submitted intent includes `strategy_id`, `strategy_run_id`, `decision_id`, `trigger_id`, `trace_id`.
- FR2: Execution service persists immutable audit events for lifecycle stages.
- FR3: Open-order, fill, position views remain strategy-scoped.
- FR4: Parent-child mapping is mandatory when router mode is netted.
- FR5: Reconciliation emits explicit corrective actions with causality references.
- FR6: Support idempotent resubmission on retries (same `intent_id` no duplicate live order).
- FR7: Establish single source of truth for lineage queries: `core_order_event` (or equivalent immutable event table).
- FR8: Define deterministic ID generation owners and formats for all IDs in execution path.
- FR9: Enforce parent/child accounting invariants in netted mode.

## 7. Quality Requirements
- QR1: P99 decision-to-intent persistence < 50ms.
- QR2: P99 intent-to-order-submit < 300ms in paper mode.
- QR3: 100% of execution logs are structured and carry tracing fields.
- QR4: Replay parity for deterministic test set >= 99.9% event match.
- QR5: Critical trace fields (`strategy_id`, `decision_id`, `trace_id`, `order_id`) coverage is 100% on critical events.
- QR6: Rollback RTO < 5 minutes, RPO = 0 for attribution fields.

## 8. Data and Observability Requirements
- Required fields in execution logs:
  - timestamp, level, event, strategy_id, strategy_run_id, symbol
  - trigger_id, decision_id, intent_id, order_id, broker_order_id
  - trace_id, causation_id, mode(direct/netted), result
- Required metrics:
  - `execution_intent_total{strategy_id,result}`
  - `execution_order_submit_latency_ms{strategy_id,mode}`
  - `execution_trace_missing_total{field}`
  - `reconciler_correction_total{strategy_id,reason}`
  - `netting_parent_child_imbalance_total{symbol}`
- Cardinality rule:
  - `trace_id`, `decision_id`, `intent_id`, `order_id` must not be used as metric labels.
  - High-cardinality IDs live in logs/events only.

## 8.1 Source of Truth
- Immutable `core_order_event` is the only authoritative store for lineage/audit queries.
- Logs are auxiliary evidence only and cannot override event-table truth.

## 8.2 ID Ownership and Format
- `strategy_run_id`: generated by strategy lifecycle loader at strategy initialize/reload boundary.
- `trigger_id`: generated at feature/market event ingress, or synthesized by compatibility adapter.
- `decision_id`: generated by strategy layer.
- `intent_id`: generated by execution ingress from idempotency key.
- `order_id`: generated by execution persistence layer.
- `fill_id`: generated from broker execution event or deterministic fallback hash.
- `trace_id`: propagated from decision; if absent, generated at ingress and recorded as synthetic.
- Format: UUIDv7 preferred for generated IDs.

## 8.3 Idempotency Key
- Required idempotency key for intent dedupe:
  - `strategy_id + strategy_run_id + decision_id + symbol + normalized_target_qty + ts_bucket`.
- Duplicate key must not create a new live broker order.

## 8.4 Netted Accounting Invariants
- Invariant I1: `parent_fill_qty == sum(child_allocated_fill_qty) ± residual`.
- Invariant I2: residual allocation rule is deterministic and documented.
- Invariant I3: child allocation never exceeds child remaining requested quantity.
- Invariant violations are P0.

## 9. Edge Cases
- EC1: Same strategy code loaded twice with different `strategy_id` on same symbol.
- EC2: Same `strategy_id` reloaded intraday -> new `strategy_run_id` must be generated.
- EC3: Parent broker order partially fills while one child strategy is paused.
- EC4: Broker reconnect causes duplicate order update stream.
- EC5: Reconciler finds orphan parent without child map.

## 10. Rollout Requirements
- RR1: Feature flags default OFF.
- RR2: Shadow validation enabled first, no execution behavior changes.
- RR3: Canary by strategy_id allowlist in paper mode for at least 5 trading days.
- RR4: Promotion gate requires all acceptance criteria pass.
- RR5: Failure-injection suite pass is mandatory before canary promotion.
- RR6: Rollback drill pass (RTO/RPO targets) is mandatory before production enablement.

## 11. Deliverables
- D1: schema pack (`schema/strategy_engine/*.schema.json`)
- D2: execution and reconciliation trace contract
- D3: test matrix and acceptance checklist
- D4: runbook for rollout and rollback
- D5: executable validation scripts/queries with pass-fail thresholds

## 12. Risks
- R1: Legacy strategy code missing `trigger_id`.
- R2: Event fanout complexity under high fill rate.
- R3: Partial backward compatibility in old dashboards.
- R4: Duplicate/late/out-of-order broker callbacks can break attribution if dedupe is weak.
- R5: Hidden latency regressions without stage-level budget monitoring.

## 13. Mitigations
- M1: Ingress auto-generate `trigger_id` if absent and mark `trigger_source="synthetic"`.
- M2: Deterministic allocator test vectors for fanout.
- M3: Dashboard compatibility layer maps legacy and new fields.
- M4: Failure-injection tests for duplicate/late/out-of-order callbacks.
- M5: Stage-level latency SLOs and regression alarms per execution segment.
