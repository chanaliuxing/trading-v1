# Multi-Strategy Engine Blueprint

## Goal
Build a generalized strategy engine that supports:
- many strategies running concurrently
- many strategies trading the same symbol concurrently
- full traceability from market trigger -> decision -> intent -> order -> fill -> position
- strict isolation so one strategy cannot mutate another strategy's state

This design is prepared for staged integration into `run_system.py` behind feature flags.

## Design Principles
- Isolation first: strategy state, risk quota, order lifecycle, and reconciliation are scoped by IDs.
- Trace everything: every event carries identity and causality fields.
- Deterministic replay: same inputs should reconstruct the same decision chain.
- Backward compatible rollout: default runtime behavior unchanged until explicit enablement.

## Identity Model
- `strategy_id`: logical strategy identifier from config.
- `strategy_run_id`: runtime instance ID for one boot/session of a strategy.
- `trigger_id`: unique source event ID (bar/tick/signal) that started decisioning.
- `decision_id`: strategy decision ID (already present in current envelope).
- `intent_id`: execution intent ID generated by execution ingress.
- `order_id`: internal order ID (DB primary order identity).
- `broker_order_id`: broker-facing order identity.
- `parent_order_id`: parent order identity for netted routing.
- `fill_id`: fill identity.
- `trace_id`: end-to-end correlation ID.
- `causation_id`: direct parent event ID in the chain.

## Required Invariants
- No order/fill event can exist without `strategy_id`, `strategy_run_id`, `trace_id`.
- `decision_id` must map to exactly one `strategy_id`.
- `broker_order_id` can map to multiple strategies only through netted parent-child model.
- Reconciler never updates rows outside `(strategy_id, strategy_run_id)` scope.
- Every critical log line in execution path includes: `strategy_id`, `decision_id`, `order_id`, `broker_order_id`, `trace_id` when available.

## Runtime Architecture
- Strategy layer: produces `DecisionEnvelope` with `decision_id` and `extras.trigger_id`.
- Execution ingress: validates schema, enriches IDs, persists immutable `intent_received` event.
- Router:
  - direct mode: one strategy -> one broker order path
  - netted mode: many strategy child intents -> one parent broker order
- Safety kernel: broker guardrails, idempotency checks, OCO lifecycle.
- Fill fanout: maps parent fills back to child intents deterministically.
- Reconciliation: verifies DB vs broker and emits corrective events with full causality.
- Observability: metrics + structured logs + audit events.

## State Isolation Rules
- In-memory caches keyed by `(strategy_run_id, symbol)`.
- Durable state files keyed by `strategy_id` at minimum, optionally `strategy_run_id` when intraday warm-restart isolation is required.
- Risk reservation keys: `(strategy_id, symbol, decision_id)`.
- Open-order queries always filter by `strategy_id`; netting parent lookup uses explicit parent-child join.

## Integration Contract with run_system
- Phase 0: docs/schema/tests only, no behavior change.
- Phase 1: add tracing fields pass-through (write-only) in execution path.
- Phase 2: enable strict validation in shadow mode.
- Phase 3: canary strategy IDs in paper mode.
- Phase 4: wider rollout with netting and fanout feature flags.
